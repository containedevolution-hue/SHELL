# Chat native desk

Chat is the owner's lab. Provider applications are complete native clients working inside that lab; they are not recreated, embedded, cropped, proxied, or replaced by browser/API imitations.

Shell reserves one visible native window slot inside the Chat layout. The Chat application remains behind and around that slot, providing desk bubbles, Seed, connection status, and lab controls. Shell identifies a registered provider application, starts it when absent or reacquires its existing window, and asks the active compositor to place that top-level surface precisely over the reserved slot. Hyprland is the first Linux target. It controls placement, focus, workspace membership, animation, and decoration; it is not the application launcher or the renderer of provider content.

Only one provider client occupies the slot at a time. Selecting another desk atomically parks the current window on a Shell-owned holding workspace and attaches the requested window. Parked applications keep running. Selecting the former desk returns the same process, native window, account surface, conversation, permissions, tools, and remote work whenever the provider itself preserves them.

Closing a Chat bubble parks its client. Closing Chat detaches every managed client and returns or parks its real window according to the session recovery policy; it never terminates the provider process. Application termination remains an explicit action in the original application or a separate Shell process-management surface. Reopening Chat reacquires eligible running windows only after verifying their registered application identity.

## Capability rule

Capability preservation is a release gate, not a preference. A client enters the lab slot only when Shell can present the complete downloaded/native application. The integration fails if entering Chat removes repository, terminal, local-file, tool, voice, remote-session, account, conversation, or provider-specific capability that works in the same application outside Chat. Unsupported clients remain ordinary standalone applications; Chat states the limitation and never substitutes a generic webpage or metered API conversation.

## Troubleshooting escape hatch

Every desk has **Troubleshoot** and **Open app separately**. The latter moves the same native session out of the lab into an ordinary visible workspace. The user tests the disputed capability in the original surface, then chooses **Return to Lab** to reattach the same session.

Shell reports only observable facts: application found, process running, window attached, required Shell permissions, remote-session continuity, and the last attach/detach result. It does not infer provider account identity or capability from a window title. Working separately isolates the fault to Chat/Shell window management; failing separately points to the provider application, account, permission, or connection; failure to launch points to installation or discovery; a wrong conversation/account points to session routing.

Troubleshooting never collects passwords, clears provider data, changes an installation, terminates a process, resets a session, or performs a repair without a separate explicit action.

## Slice 3 foundation

The first executable host foundation now lives in `node-sidecar/lib/native-desk-*.js` and `hyprland-native-desk.js`. It loads only Shell's trusted registry, verifies exact initial class plus `/proc` executable identity, derives a process-start-bound session id, serializes mutations, parks rather than closes, preserves the exact window through standalone and return, and blocks new changes until observation reconciles an uncertain compositor result. The Hyprland adapter selects windows only by compositor address and contains no close, kill, terminate, credential, URL, or arbitrary-command operation.

The shipped registry is empty and the general capability discovery reports window management as planned. Enabling the adapter requires an explicit local Shell flag, an explicit `legacy-0.55` command profile, Hyprland `0.55.x`, a real compositor session, a validated provider registry entry, and a trusted caller that supplies the acceptance result. Page content cannot enable it. The [authenticated in-process bridge](../../contracts/chat/IN-PROCESS-BRIDGE.md) now binds one exact native peer and Chat process/window identity, validates fresh trusted geometry, serializes observation/management/close, and revokes on identity or geometry loss. Changed geometry parks the previous overlay before adopting new coordinates. Unknown compositor results block every provider's mutations until reconciliation. Production window creation and native geometry callbacks remain pending; there is no unauthenticated loopback management endpoint.

The canonical Chat acceptance lane is separate from the public app store. Shell accepts only the private `chat` `0.1.0-dev` acceptance release at SHA-256 `2261aba0f5a2b8d79339d5072e992c7457c7a9e9ce8139e5c3246a804ff4d1b7`, with `storage.chat.preferences.local` as its only required capability. It installs under Shell's private acceptance data directory and is never listed by the starter catalog or `/v1/apps`. Static assets are served without an authority token at the fixed loopback acceptance path; native authority stays in the private bridge. When Shell is launched with `SHELL_CHAT_ACCEPTANCE_WINDOW=enabled`, two fixed Tools-menu commands can open or close one disposable window. Opening revalidates every installed file. Rust then samples the real PID, HWND, inner-frame position, inner viewport, monitor and DPI every 250 ms over the authenticated inherited channel. The host binding fixes the installed digest, `chat-acceptance` label, exact loopback index URL, process, native session, window, frame, navigation, and fresh geometry. Navigation, destruction, hiding, replacement, stale geometry, or a monitor/frame mismatch revokes the bridge and closes only this disposable window. No geometry or authority is exposed to its page, it is absent from Tauri's startup windows, and provider acceptance remains false.

The controller also has a default-off Windows backend boundary. Registration uses the stable package-family name, application user model id, package-relative executable, and exact window class rather than a mutable title or versioned `WindowsApps` path. Runtime identity binds those values to the pid, process start time, and HWND. The backend only minimizes, restores, places, and focuses a revalidated exact window; it contains no close, hide, terminate, arbitrary-command, arbitrary-path, `SetParent`, or focus-policy-bypass operation. Elevated and foreign-virtual-desktop windows are denied.

This is not accepted live Windows window control. The private `cfg(windows)` Rust driver enumerates and revalidates exact packaged window identity and offers only activation, minimization, placement restoration, placement, and focus for registry-resolved verified tokens. Tauri and its exact Node child now exchange size-bounded HMAC-authenticated frames through inherited stdin/stdout pipes, bound to a random launch session plus both process ids. Requests carry only a registered `clientId`, opaque window reference, fixed lifecycle operation, and bounded trusted geometry; malformed or late frames fail closed, and no socket or page-visible command exists. The launch secret is removed from Node's environment before it can reach child processes. The production provider registry stays empty, the canonical Chat binding has only fake lifecycle proof, and runtime acceptance has not passed, so the manager remains unavailable.

## Proof still required

Deterministic pressure tests do not establish live placement. A real Hyprland session must still prove the registered downloaded application, atomic batch behavior and recovery, same-window reattachment, multi-monitor coordinates, focus recovery, provider crash/restart, Chat crash/restart, logout, suspend/resume, remote-session survival, reduced-motion behavior, and side-by-side capability comparison for every supported client. The [separate test-session procedure](../../os/CHAT-HYPRLAND-TEST.md) preserves KDE recovery and includes a read-only identity collector. The installed Hyprland command profile must be captured as evidence. Until those gates pass on the target Shell installation, Shell reports the native desk manager unavailable.

Windows now has authenticated private Rust-to-Node caller wiring and a real disposable Chat geometry producer. The remaining hardware gate is provider acceptance: collect and review exact package/window identity, then explicitly register each accepted client; prove physical mixed-DPI/multi-monitor placement, operating-system focus behavior, package update/restart handling, recoverable minimization, exact A-B-A return, crash recovery, remote-session survival, and a side-by-side capability comparison. Installed package observations are discovery evidence, not acceptance. Until those platform gates pass, the registry remains empty and Windows reports the native desk manager unavailable.

### Windows observation checkpoint

From a PowerShell in the Shell repository, launch a development build with `$env:SHELL_CHAT_ACCEPTANCE_WINDOW='enabled'; npm run dev`. Shell still opens normally; the acceptance window does not. Choose **Tools → Open disposable Chat acceptance**, confirm that the private Chat lab renders, move it once across each intended monitor, resize it, and close it with **Tools → Close disposable Chat acceptance**. A navigation attempt away from the exact local index, hiding/destruction, or an invalid monitor transition must close the disposable window and require a fresh open. This checkpoint may close only that window and must not attach to ChatGPT or Claude.

After exact provider identities have been captured with `node scripts/capture-chat-native-evidence.js --platform win32 --out <private-evidence-file>` and reviewed into the currently empty registry in a separate approval step, the user-observed A-B-A gate is: open the downloaded ChatGPT and Claude apps independently; confirm account, conversation, tools, terminal/repository and remote access in each; attach A, switch to B, return to A; confirm both exact processes/windows and conversations survived; repeat across monitors and DPI boundaries; use **Open app separately** and **Return to Lab**; then repeat after provider restart, Chat restart, Shell restart, suspend/resume, and the normal phone remote workflow. Any capability loss or identity ambiguity fails acceptance and leaves that client standalone.
